## Design Decisions & Empirical Findings

- **Validator Deduplication (Main-Scope Drift Fix)**:
  `KafkaTaskListener` previously contained a duplicate private implementation of `validate(TaskEnvelope)`. This was rewired to call `EnvelopeValidator.validate(envelope)`. When semantic validation fails (blank prompt, out-of-range breadth, non-positive deadline/budget), `EnvelopeValidator` throws `TaskValidationException`. `KafkaTaskListener` catches `JacksonException | TaskValidationException` and routes the record to `poison()` (replies `{"task_id":null,"status":"INVALID","error":"..."}` and copies raw record to `adaptive-tasks-request-dlt`). `KafkaIngressIntegrationTest` remained 100% green.
- **Decision JSON Parity (Empirical Finding)**:
  When an envelope specifies `forced_topology` (e.g. `CHAIN` or `FAN_OUT`), `RoutingService.route()` sets `source = DecisionSource.OVERRIDE`, `rationale = "forced_topology override from ingress"`, and `verdict = null`. The resulting `tasks.decision` JSON is:
  `{"verdict":null,"source":"OVERRIDE","rationale":"forced_topology override from ingress"}`.
  This contains no task ID, timestamps, or transient metadata, and is byte-identical across REST, Kafka, and MCP submissions.
- **Result Normalization & Hash Equality (Empirical Finding)**:
  `tasks.result` generated by `ChainGraphFactory` builds a structured JSON root:
  `{"plan":"...","summary":"...","citations":[...],"degraded":false}`.
  Under the deterministic test doubles (`FixedTextChatModel` repeating canned summary and `SearchTool` returning canned citations), the terminal results are completely deterministic. No task IDs or timestamps are embedded into `tasks.result`. `normalizeResult()` defensively strips `task_id`, `timestamp`, `created_at`, and `updated_at` if present and re-serializes via `ObjectMapper`. The SHA-256 hex digest of the normalized result JSON is identical across all three transports: `sha256(REST) == sha256(Kafka) == sha256(MCP)`.
- **Auth Matrix Verification**:
  - REST: `POST /tasks` without `X-API-Key` returns HTTP 401; with `X-API-Key: test-key` returns HTTP 202.
  - MCP: `POST /mcp` tool execution succeeds without any API key (client sends no credentials); raw `GET /mcp` without key returns non-401.
  - Kafka: message sent to `adaptive-tasks-request` without credentials receives ACK on `adaptive-tasks-reply` (local broker transport, no application auth header).
- **Execution Discipline**:
  Submissions and task completions are awaited sequentially within each test scenario to prevent concurrent table creation locks in PostgreSQL (avoiding PostgresSaver checkpoint relation deadlocks).
